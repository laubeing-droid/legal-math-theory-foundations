## 3. 近似词法状态机（不是 Lean parser）

### 3.1 规则

对每个文件的 UTF-8 文本（保留 BOM）做单次扫描，状态包括：code、line comment、block comment（深度计数）、string（反斜杠转义）、尽力处理的 `s!"` 插值（花括号深度）。在 code 状态且前一字符不是标识符续写字符时，尝试识别字符字面量（含以 `"` 或 `\` 为内容的字面量）。块注释内再遇到 `/-` 则深度加一，遇到 `-/` 则减一。

掩码之后，用与生成器相同的 `DECL_RE` / `IMPORT_RE` 抽取行首声明与 import。生成器对照组则仍用其 `COMMENT_RE`（`/-[-!]?.*?-/` 与 `--`，非嵌套、非贪婪）去注释。

### 3.2 明确不是什么

这不是 Lean 4 tokeniser、parser 或 elaborator。未保证 raw string、宏展开、插值内部注释、完整字符转义表、以及 `axiom` / `class` / `instance` 等未进入 `DECL_RE` 的种类。namespace 列来自对 `namespace` / `section` / `end` 的行首词法堆栈，不是作用域检查器。

### 3.3 与生成器同口径 vs 语法差异：两处实例

**（1）ByteSyntax.lean——状态机局限，不是清册错误。**

`proofs/lean/juris_lean/JurisLean/FullMath/Document/ByteSyntax.lean` 约第 27 行：

```
def quoteByte : Char := '"'
def escapeByte : Char := '\'
```

补字符字面量规则之前，状态机把 `'"'` 里的双引号当成字符串起点，落入未闭合字符串，把后续定理掩掉，theorem 从 14 计成 1。生成器 `COMMENT_RE` 并不进入字符串状态，因此一直是 14，与清册一致。补规则之后三者对齐。这只能说明「近似状态机曾漏掉一种 Lean 字符字面量写法」，不能说明源码或清册有冲突。

本轮在全部 678 份中识别到 3 个文件共 10 处字符字面量；补规则后 theorem/lemma/def/structure/inductive 及保留 BOM 的 import 集合，状态机与生成器 **0 差**，theorem/lemma 并与清册 0 差。未闭合 0。

**（2）LegacyConeBridge.lean——生成器非嵌套口径 vs 嵌套规则，计数未变。**

这是 678 份里唯一 `block_nested_open>0` 的文件，最大深度 2。第 436–441 行：

```
/-! ============================================================
    第六节 闭合项归约（G2 判据③的主面）
    —— 本节用 `/-! -/` 横幅而不是 `section/end`，因为
    ...
    ============================================================ -/
```

横幅已在块注释中，又在反引号里写出 `/-! -/`。状态机在此深度变为 2，随即被内层 `-/` 降回 1，到第 441 行才真正结束外层注释。生成器 `COMMENT_RE` 在第一次看到 `-/`（即反引号那段的结尾）就结束注释，于是第 438 行后半到第 441 行被当成代码。那些行是缩进散文，不是行首 `theorem` 或 `import`，所以被计声明数与 import 集合不变。

差异属「生成器同口径（非嵌套正则）与嵌套块注释规则」不同，不是 Lean parser 对这段注释的裁决，也不得升级为清册错误。若有人把生成器提前闭合后的散文当成代码编辑，才可能引入风险；当前计数不受影响。
