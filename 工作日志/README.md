# 工作日志怎么写

看板回答“任务走到哪一步”，工作日志回答“谁在什么时候做了什么、读了哪个版本、留下什么、下一位怎么接”。十几个 Agent 可以并行，但不能只靠移动卡片交接。

任务详情和检查证据写在对应 Issue；[日总日志](20261113_工作总日志.md)只追加重要变化、阻碍和交接，不另建一套任务状态。任务状态仍以 [Projects 看板](https://github.com/users/laubeing-droid/projects/2) 为准。

## 每次交接写这九项

- 北京时间：实际记录时刻；事件发生时间不同则另注明。
- 任务与看板卡：Issue 链接、看板卡链接；尚未对应写“待关联”，不要编编号。
- 执行者：实际执行者；计划人选另写，不当作已经接单。
- 基线：仓库、分支、commit；本地材料另记电脑和相对目录。没读到写未确认。
- 已做：具体动作和已读范围；收到报告与亲自核验分开。
- 成果链接：文件、提交或核查证据；没有就写无。
- 待办：下一步及接手人；尚未确定则明说。
- 阻碍：缺件、权限、版本冲突或其他问题；没有核实不猜原因。
- 交接：交给谁、交什么、是否收到确认。

无需为每个 Agent 再建一套日报。执行者在 Issue 留任务记录，总协调把跨任务变化和重要交接追加到当天总日志。派单、开始、收件、核查、阻碍与移交都要说清；创建文件不等于任务完成。

## 并行和纠错

日总日志以追加为主。写入前重新读取最新文件，按当前版本提交，避免覆盖别人的追加。发现错误，追加更正并指向旧记录；涉及敏感信息须立即报告并按授权处理，不以“保留历史”为由继续扩散。

日志不收私人案件原文、凭据、原始聊天或无关个人信息。不得把目录清单当成文件已读，不得把测试源码当成运行通过。第三步仍仅静态阅读和比对，不运行、不编译、不测试、不改代码。

新建每日总日志使用 `YYYYMMDD_工作总日志.md`；单项交付继续按排班规定的五段命名。这里的 README 只作固定入口。

## 轻量多 Agent 协作

不用安装 SDK 或调度服务。以已有工具落实任务分配、独立产物、明确交接和统一收件：

1. 总协调给每项任务指定负责人，写清范围、输入版本、预期产物、完成条件和阻碍；先核实权限，再派单。
2. 按章节、模块或目录分批覆盖。每批分别列已读和未读范围，不能由抽查推称全量完成。
3. 执行者分别产出带日期、版本和署名的稿件；统一送中转区，审查前不进入正式稿。这是协作隔离，不等于已经建立技术沙箱。
4. 同一文件或结论发生碰撞，记录双方版本和分歧，交总协调指定合并人。写入前重新读取最新文件；保留双方稿，不覆盖、不抢写。
5. 交接须包括成果、基线、检查范围、剩余问题和下一位负责人。接收者确认收到后才算交接到位，不等于验收通过。
6. 卡片是唯一任务状态源；Issue 保存详情与证据，日总日志只记录变化和交接，不复制整张看板。

### 2. 分片、认领与单写责任

分片编号使用 `I03-S01` 一类格式：I03 是 Issue #3，S01 是该任务的分片。总协调在 Issue 分配编号，执行者不自行重复占号。每片按一个明确输入范围划分，例如“某仓某 commit 的三个指定 Markdown”，不写“把所有东西看一遍”。

一个分片只有一名主负责人、一个单写产物。可以安排独立评审者，但评审写自己的文件，不共同编辑主稿。总协调可接收认领；**只有总协调确认范围、基线和负责人后才算派单成立**。重复认领、范围重叠或上轮未释放的分片先停写，由总协调决定拆分或移交。需要扩大范围先回报，不顺手接管其他任务。

派单模板（写 Issue）：

> 分片：I__-S__；北京时间：____  
> 主负责人／评审者：____／____；派单者：____  
> 输入：电脑或仓库＋相对路径＋commit／版本；未确认项：____  
> 覆盖：____；明确不读／不改：____  
> 工作方式：静态只读；禁止运行、修改旧仓及覆盖他人稿件  
> 独立产物路径：____；完成条件：____  
> 单写负责人：____；交给谁收件：____  
> 依赖、权限、阻碍：____；用户已授权范围：____

接单回执模板：

> 收到分片____，接单时间____，执行者____。  
> 能访问的输入及版本____；不能访问____。  
> 与本人/其他分片重叠____；接受的产物路径____。  
> 已理解禁区____；预计先交的批次____。  
> 本回执表示收到并核对范围，不表示阅读或任务完成。

### 3. 统一收件与独立产物

每 Agent 每分片用自己的新文件：
`YYYYMMDD_任务分片_内容_版本_执行者.md`。
示例：`20261113_I04-S01_数学前提评审_v0.1_Grok.md`。这是示例，不表示已派单。

稿件进入中转区；数学稿进入数学理论集中区。后续修订升版本，保留原件。不能把“相同文件名”当覆盖许可。收件者先核对文件可读、分片编号、基线、覆盖和作者，再在原 Issue 留链接；正式采纳由指定统稿人负责，不能由收件人自称完成学术验收。

### 4. 覆盖、工作日志与交接模板

每批在对应 Issue 使用同一个覆盖表；日总日志只贴交接链接和重大变化。可用一行表示一个范围，但必须能据此找到具体文件。

| 分片／批次 | 来源电脑/仓＋相对范围 | commit/版本/哈希 | 清点到 | 实际已读范围 | 未读/跳过及原因 | 产物与检查证据 | 接手位置 |
|---|---|---|---|---|---|---|---|
| 待填写 | 待确认 | 未取得写未确认 | 文件数或明确清单 | 文件及章节/行段 | 不留空冒充全读 | 无则写无 | 下一文件/章节 |

哈希只能证明指定字节是否相同，不能证明读过、来源独立、法律正确或可以互换。记录算法和比较对象；同内容跨仓仍保留每个来源。哈希未取得就写未取得，不为凑证据临时运行项目程序。去重只限已比较的文件，不能由9目录样本推称全仓去重。重复文件仅标记，**不删除**。统计“发现”“已读”“已核”分开，不能用已列目录数量作阅读完成率。

工作记录与交接可直接复制：

> 北京时间____；分片____；实际执行者____；基线____。  
> 已做____；实际已读____；未读____；证据链接____。  
> 发现／建议／未核分列____。  
> 下一步____；阻碍____；交给____；接收确认____。  
> 是否运行：否（今晚）；是否改旧仓：否。若事实不同必须如实报告，不填假模板。  
> 恢复应从____继续；不得重做的已完成范围____。

### 5. 并发碰撞处理

任何写入前读取目标最新版本。输入或输出已有新提交，停止用旧内容覆盖，先比较新旧基线。无法确认安全合并时交总协调，不强推。

日总日志与正式统稿由总协调或其明确指定的单写负责人维护；执行者先在自己的 Issue 评论/独立稿交接，避免十几人同时改总日志。指定负责人变更须在原 Issue 留移交与接收确认。独立稿可并行创建，共享文件不可并行替换。

冲突记录写四项：双方分片及版本、冲突位置、各自主张与依据、需要谁决定。总协调决定排班和文件合并方式；法律或数学实质争议保留双方意见，送指定评审，必要时请用户定案。总协调不能为合并方便宣布待核法源正确。敏感信息、授权边界或越范围问题先停该部分，不阻塞无关已授权工作。

### 6. 收件与验收清单

在原 Issue 勾选，不复制第二套状态：

- [ ] 产物、作者、分片、基线和覆盖范围齐全，文件能打开。
- [ ] 引用能回查；待核与已核分开；未读未运行不冒称完成。
- [ ] 全量任务所有分片有覆盖证据，或明确列出未完成范围。
- [ ] 法律对应、数学前提、证明状态、程序实现证据分别检查。
- [ ] 无私人材料泄露，无未经授权写入、运行或覆盖。
- [ ] 冲突有处理结论或明确保留；后续任务和接手人清楚。
- [ ] 指定评审者给出“接受／退回修改／有条件接受”及理由。

收件不等于接受，有条件接受不等于全部完成。执行者提交后进入待检查；总协调根据指定评审和完成标准更新卡片。第6步未开展的运行验证不能靠静态审计勾成通过。

### 7. 中断与恢复

中断前在 Issue 留最后已读位置、输入版本、已上传产物、未提交的内容及阻碍；不要仅说“继续”。没有写完的原稿单独交 v0.x，注明不完整，不覆盖别人文件。

恢复顺序：先读原 Issue 最新交接 → 核查输入版本和权限是否变化 → 确认分片仍由本人负责 → 从覆盖表接手位置继续。基线变化时另记差异覆盖，旧结论保留原版本；不能把旧完成率照搬。新接手者须回执，上一执行者停止写同一产物。失败的上传先查是否已存在，避免重复提交。
